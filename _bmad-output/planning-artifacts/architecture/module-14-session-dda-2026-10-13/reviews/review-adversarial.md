# Adversarial Review — Module 14 Session Control and DDA

**Verdict:** NOT READY FOR IMPLEMENTATION. The architectural direction is strong, but the current contracts still permit mutually incompatible implementations at the exact boundaries that are supposed to guarantee single-writer behavior, graceful draining, durable result accounting, and calibrated `/move-plan` actuation.

## Findings

- The claimed “final fence revalidation immediately before the irreversible effect” does not close the check-to-effect race. Implementation A can commit a successful fence check, be suspended, lose the lease, then wake and click or move after implementation B has acquired a higher fence. IndexedDB cannot atomically fence an external DOM side effect. Define a durable effect-claim protocol with explicit states and a takeover exclusion window, require the lease to remain unexpired through dispatch, and specify how a successor reconciles a claimed-but-unconfirmed effect instead of issuing it again. The acceptance criterion must test a takeover between the final transaction commit and the actual `click()`/move call.

- Lease time semantics are underspecified and inconsistent with the session clock rule. The session uses `effectiveNowMs=max(Date.now(),lastObservedEpochMs)`, but lease acquisition, expiry, renewal cadence, maximum pause, and backward/forward wall-clock jumps are not defined. One implementation can compare raw `Date.now()` while another uses a persisted monotonic floor, producing simultaneous owners after a clock adjustment. Specify the authoritative lease clock algorithm, renewal interval, lease duration, takeover guard, and whether renewal increments `fencingToken` or only ownership acquisition does.

- The IndexedDB authority is only single-origin, while the stated browser-tab guarantee is broader. Tabs on `www.chess.com`, another Chess.com origin/subdomain, an embedded frame, or a userscript execution world with a different storage partition can have independent IndexedDB databases and BroadcastChannels, so both legitimately become leader. Either constrain and validate one canonical origin/execution context, or move the lease to an authority shared across all supported contexts. A GM notification cannot repair this because the document explicitly forbids GM storage from being concurrent truth.

- `QueueIntent` does not resolve the crash ambiguity it is intended to solve. After persisting an intent, a tab may crash before the click, during the click, or after the platform accepted the click but before any acknowledgement. On recovery, one compliant implementation can re-click the still-pending intent; another can wait forever; a third can expire it and complete while matchmaking later creates a game. Define a queue-effect state machine such as `PREPARED → CLAIMED → DISPATCHED → MATCH_OBSERVED/CANCELLED`, the evidence required for each transition, and a recovery rule that never blindly replays an ambiguous click.

- Queue draining has no bounded or authoritative termination. “Queue intent expires without game” is a transition, but no `intentExpiresAtEpochMs`, matchmaking acknowledgement, cancellation protocol, maximum drain duration, or late-match behavior exists in the DTOs. One implementation may complete after 30 seconds and abandon a game that appears at 31 seconds; another may remain `DRAINING` forever. Persist the queue-intent deadline and platform acknowledgement, define cancellation/late-binding behavior, and state whether an observed game after session completion must be rejected, adopted for drain, or surfaced for manual handling.

- Manual stop semantics are incomplete. The transition table defines TTL handling for `QUEUEING` and stop handling only for `IN_GAME`; the test matrix mentions a distinct forced stop without defining its command, authorization, or effect. Implementations can disagree about whether graceful stop cancels an unclicked intent, drains a dispatched intent, or completes immediately, and whether forced stop can abandon an active game. Add exact `REQUEST_GRACEFUL_STOP` and `FORCE_STOP` transitions for every nonterminal phase, including their queue-intent and active-game effects.

- `PAUSED` is an overloaded state without a deterministic substate or transition table. It covers storage failure, account mismatch, uncertain opponent, lost context, and calibration failure; Auto Move is conditionally allowed, but TTL expiry, terminal result, lease takeover, recovery, and graceful stop while paused are not defined. Two reducers can persist different next states for the same event sequence and both match the prose. Persist a typed pause class plus the pre-pause work state, and define a full event matrix for `PAUSED`, or replace it with explicit phases such as `PAUSED_QUEUEING` and `PAUSED_IN_GAME`.

- The current-game continuation rule contradicts the persistence failure rule. AD-10 says an admitted game may finish under the last durable snapshot, while the failure table says an IndexedDB write failure drains “if safe”; yet every move requires fence/revision validation in IndexedDB and result commit must be durable. An implementation that keeps moving cannot advance durable position revision or prove its fence, while one that stops violates graceful completion. Define precisely which storage operations are mandatory for each subsequent move and make storage-loss behavior unambiguous; fail-closed Auto Move is the only defensible default unless a separately durable write path exists.

- The game-level “controlling versus non-controlling” predicate is missing. AD-5 excludes unactuated outcomes, the response rules invalidate shadow/fallback/mismatch moves, and `ActiveGame.actuation` counts applied and non-applied moves, but the design never says whether one non-applied move, only the first move, a threshold, or any mismatch invalidates the whole game. Different implementations will produce different W/D/L inputs and therefore different DDA modes from identical games. Define a deterministic predicate (for example, every engine-selected move must be calibration-applied) and persist the first invalidation reason irreversibly.

- The request cannot enforce the calibration identity that the response is required to match. `ActiveGame` pins `scaleId`, `artifactChecksum`, and `artifactVersion`, but the exact `/move-plan` payload sends none of those fields. Unless the backend already pins all three atomically by `runtimeGameToken`, an artifact promotion between capability preflight and first request can make the game invalid, and two backend implementations may choose different artifacts while honoring the same request. Add a versioned calibration requirement object to the request or normatively bind the existing backend pinning contract, including the first-request race and behavior when the pinned artifact is no longer serviceable.

- Calibration capability metadata has no exact wire contract or freshness rule. “Fresh,” “active rollout eligibility,” supported range, and authenticated preflight are guards, but no endpoint, schema, `observedAt`, expiry, rollout cohort binding, or cache invalidation policy is defined. One client can cache capability for the full session; another can refresh per game; both comply and admit different games. Specify the capability DTO, source endpoint, maximum age, binding to account/client/game cohort, and the transaction in which it is validated before admission.

- Opponent rating stability is not executable. The design demands “stable opponent identity/rating” but gives no number of observations, minimum interval, selector agreement, account-side disambiguation, provisional-rating treatment, rating-change tolerance, or timeout. One adapter can pin the first DOM number while another waits for two matching reads, producing different targets. Define a canonical `OpponentEvidence` contract and stability algorithm, including how to prevent reading the local player’s rating after board orientation or responsive-layout changes.

- Platform game identity is treated as canonical without defining canonicalization or fallback. Chess.com URLs, live-game identifiers, rematches, reconnects, and DOM attributes can expose different or delayed IDs. Deduplication by `(sessionId, platformGameId)` is only as strong as that mapping, and the same physical game can be counted twice if its provisional identity is later replaced. Define identity source precedence, normalization, provisional-to-canonical aliasing in one transaction, and the rule for identity absence. The `events.platformGameId` index must also be explicitly unique over the intended scope rather than merely listed as an index.

- Result provenance is insufficient to stop an old or externally started game from entering a new session. Uniqueness is session-scoped, so the same platform game can be counted in two sessions, and `START` does not state whether starting while already on a live/terminal game is rejected. Require that every countable result reference the persisted `ActiveGame`, its consumed `QueueIntent`, runtime token, account, and actuation validity; reject session start or game adoption unless an explicit, versioned adoption command establishes provenance.

- The current-session pointer is not guaranteed atomic with session creation and state updates. The document only requires events and snapshots to share a transaction, while `metadata` carries the current-session pointer and GM gets a second recovery pointer. A crash can leave a valid running session that neither pointer names, or two running sessions with ambiguous ownership. Require `metadata.currentSessionId`, the initial session snapshot, initial event, and lease/session binding to commit in one transaction; enforce at most one nonterminal session per account/context during decode and migration.

- Reset/recovery can recreate split brain. When the GM pointer references a missing/corrupt snapshot, the UI permits explicit “recover/reset,” but reset semantics do not fence old callbacks, cancel an already dispatched queue attempt, preserve an admitted game, or prevent a new session from starting over the same platform game. Define reset as a versioned terminal/audit event with a new authority epoch, forbid destructive reset while ambiguous external work exists, and require all callbacks to bind the authority epoch in addition to session revision/fence.

- TTL admission lacks the promised headroom rule. AD-10 lists “TTL headroom,” while `canQueue` only checks `effectiveNowMs < deadlineEpochMs`. A compliant implementation can admit at deadline minus one millisecond and then drain an entire game well past the configured duration; another can impose an arbitrary five-minute margin. Add `minimumAdmissionHeadroomMs` to configuration/DTO validation, define whether it covers matchmaking plus a game or only queue dispatch, and include it in the canonical admission guard.

- DRAINING has no maximum duration or abandonment/reconciliation policy for games that never emit a recognized terminal result. Network loss, a stuck modal, adjournment, platform maintenance, or an unknown outcome can leave automation and session ownership alive indefinitely, violating bounded-session expectations. Add `drainDeadlineEpochMs`, specify safe behavior at that deadline, and distinguish “automation stopped” from “result statistically reconciled” so the controller never fabricates an outcome.

- The requested behavior and the selected hysteresis behavior are observably different. The product statement says “inside the band or below” uses `+200`, whereas this design retains `CORRECT/-200` while the posterior remains inside the band after crossing the ceiling. Both can be defended as interpretations of a hysteretic band, but they yield different target sequences. Make the true two-threshold behavior an explicit ratified requirement and acceptance example, or implement the literal requested policy; do not leave implementation teams to choose.

- Saturated targets undermine the assumed actuator response but their statistical treatment is undefined. The design allows clamping and says continuation occurs “unless saturation policy trips,” yet no policy, threshold, or controller-evidence rule exists. At a rating boundary, `+200` and `-200` may collapse toward the same effective strength, so the loop can interpret outcomes as if the requested actuator were delivered. Define whether saturated games are controlling, specify a maximum saturation count/rate, and prescribe the state transition when the actuator lacks authority in the required direction.

- Auto Queue and Auto Move ownership handoff is stated as a boolean formula but not as a concurrency protocol. Existing legacy timers/callbacks may already be scheduled when Module 14 starts, pauses, loses leadership, or releases ownership; changing a gate does not cancel those callbacks unless every irreversible callback is instrumented. Define a single effect epoch shared with the existing schedulers, invalidate all prior epochs on ownership changes, and make the exit gate prove that a pre-session legacy callback cannot click or move after the session acquires control.

- User preference interaction can defeat graceful draining. `canAutoMove` requires `userAutoMove`, so toggling the preference off during `DRAINING` strands the admitted game, while the lifecycle promise says the current execution is allowed to finish. Conversely, ignoring the toggle would violate the explicit gate and user intent. Specify whether session start snapshots/locks Auto Move consent for admitted games, whether turning it off is graceful or forced stop, and how the UI communicates that consequence.

- Event sourcing and deterministic replay are not fully specified. Event schemas, causal revision, ordering, idempotency keys for non-result commands, reducer-version migration, and whether snapshots are authoritative or rebuildable are absent. One implementation may treat the snapshot as truth and logs as audit; another may replay the journal and reject a diverging snapshot. Define canonical event envelopes, expected revision, reducer/controller versions, ordering, snapshot checksum, and recovery behavior on divergence so the “byte-equivalent replay” exit gate is implementable.

- The credible interval requirement is non-deterministic as written. The design requires a 95% Beta credible interval in persisted/observable state but names no interval type, quantile algorithm, numeric precision, rounding, or library. Different implementations will reject each other’s derived snapshots as corruption even though the interval does not actuate v1. Either make the interval presentation-only and recompute without persistence validation, or specify the exact deterministic algorithm and tolerance.

- Position revision and request replay semantics are incomplete. The request ID is derived from `runtimeGameToken-positionRevision`, but the document does not define when revision increments, whether the FEN/revision commit precedes the request, how retries reuse IDs, or what happens when the same revision is observed with a corrected FEN. Define a durable observation event and monotonic transition rules, bind request ID to an observation digest, and require idempotent backend response behavior for exact retries.

- Unknown-result acknowledgement is an unspecified escape hatch. The failure table says admission blocks until the unknown outcome is “reconciled/acknowledged,” but it does not say whether acknowledgement drops the game, changes counters, marks it non-controlling, or permits a later correction. Implementations can silently skip losses and bias the controller while still claiming an acknowledged outcome. Define explicit reconciliation commands and immutable audit outcomes; manual acknowledgement must never synthesize W/D/L and any excluded game must remain visible in denominator-quality telemetry.

## Recheck — Corrected documents

**Recheck verdict:** MOST CRITICAL/HIGH FINDINGS CLOSED; NOT YET INTERNALLY COMPLETE. The revision closes the original effect TOCTOU by holding one required Web Lock across fence validation and synchronous dispatch, constrains IndexedDB authority to one canonical origin, adds durable queue-effect states, separates observed/control counts, defines calibration capability pinning and `/move-plan` schema v2, makes storage loss fail closed, specifies opponent/game identity evidence, atomically binds the current-session pointer, bounds admission/draining, invalidates legacy callbacks by epoch, and makes saturation/control eligibility explicit.

Remaining critical/high issues:

- The durable phase enum is internally inconsistent. The lifecycle table declares `IDLE`, `QUEUEING`, `IN_GAME`, `DRAINING`, `PAUSED_QUEUEING`, `PAUSED_ACTIVE`, and `COMPLETED`, but the transition table targets undeclared `ABORTED`, AD-6/recovery targets undeclared `PAUSED_STORAGE`, and failure behavior names `PAUSED_ACTIVE_STORAGE`/`PAUSED_QUEUEING_STORAGE`. A strict DTO/reducer cannot distinguish whether these are phases or reason codes, so compliant implementations will serialize incompatible snapshots. Declare every durable phase once, model storage/context values as typed `pauseReason`s, and add `ABORTED` to the phase enum/state diagram or map force-stop to an already declared terminal phase.

- TTL behavior is still undefined for queue intents in `PREPARED` and `CLAIMED`. The transition table covers “no intent” and `DISPATCHED`; AD-7 says a surviving `CLAIMED` becomes `AMBIGUOUS`, while graceful stop says it cancels an “unclaimed” intent. At the deadline, one reducer can cancel `PREPARED`, another can preserve it, and `CLAIMED` can either become ambiguous or drain, with materially different click risk. Add an exhaustive `(phase, intent.status, TTL/stop)` matrix and require that no `PREPARED` or `CLAIMED` path can dispatch after the deadline.

- The drain deadline formula is missing. The documents say start persists `drainDeadlineEpochMs` and configure `maximumDrainMs`, but never define whether the value is `startedAt+maximumDrainMs`, `deadline+maximumDrainMs`, or `enteredDrainingAt+maximumDrainMs`, nor how it is combined with `observeUntilEpochMs`. With the sample two-hour duration and two-hour maximum drain, the first interpretation allows zero graceful drain at normal TTL while the others allow two additional hours. Define the exact formula and precedence at start, TTL, manual stop, and queue-observation timeout.

- Ambiguous queue exclusion still permits a late unowned game. After a `CLAIMED`/`DISPATCHED` intent times out, an operator may close it as excluded and resume/complete the session, but there is no proof of platform cancellation, quarantine interval, or rule for a canonical game that appears afterward. A late matchmaking result can overlap a newly admitted game or run outside session ownership. Require positive cancellation evidence before re-queueing, or keep admission blocked for a defined quarantine and specify how any late game is bound, drained, or escalated without counting it.

- The exact Auto Move gate references `activeGame.platformGameId`, but the strict `ActiveGame` DTO defines only `canonicalPlatformGameId`. One implementation will always reject moves; another will add an undocumented alias. Change the gate and every guard to the canonical field name and add schema-level tests that reject the obsolete property.

- Position revision and retry semantics remain non-executable. The request ID uses `<runtimeGameToken>-<positionRevision>`, but the documents still do not define the atomic event that increments the revision, whether FEN/observation commit occurs before the request, whether exact retries reuse the request ID, or how a corrected FEN for the same board observation is handled. This leaves reload/network retry capable of either duplicate analysis or identity collision. Specify the durable observation transition and backend idempotency contract for identical and conflicting retries.

- The controller policy remains explicitly marked `[ASSUMPTION]` and differs from the literal product rule. The design retains `CORRECT/-200` inside the band after crossing the ceiling; the request says “inside the band or below” uses `+200`. This is now clearly exposed rather than hidden, but implementation should not begin until the product owner ratifies true two-threshold hysteresis or the contract is changed to the literal policy.

## Recheck 2 — Post-fix documents

**Recheck verdict:** NO REMAINING CRITICAL SAFETY FINDING. Multi-tab exclusion, irreversible-effect fencing, queue ambiguity, TTL intent handling, bounded drain timing, late-match quarantine, canonical game identity, exact position revision/retry, calibration identity, and the obsolete Auto Move field are now closed. The following high contract issues remain:

- Failure behavior still names undeclared phase `PAUSED_CONTEXT` for opponent/account failures even though the document says durable `phase` is exactly one of eight values and context details must be `pauseReason`s. Drain timeout is also described only as terminal `UNRECONCILED_DRAIN_TIMEOUT` without selecting `COMPLETED` or `ABORTED`. Replace `PAUSED_CONTEXT/...` with `PAUSED_ACTIVE` or `PAUSED_QUEUEING` plus the typed reason, and assign an exact terminal phase for drain timeout; otherwise strict decoders and reducers remain incompatible.

- The saturation safety gate is not representable by the strict DTOs. The prose requires a persisted count of consecutive saturated controller-eligible games in the same mode, but `SessionSnapshot.controller` contains no such field, and `maximumConsecutiveSaturatedGames` appears in configuration without a validation rule. Add the durable counter/mode fields, reset/increment transitions, integer bounds for the configuration value, and an acceptance test for the exact pause boundary.

- `PAUSED_ACTIVE` says Auto Move may run when a typed reason “explicitly permits durable drain,” but no normative reason-to-permission table exists. The generic transition for context/calibration failures likewise allows either a paused phase or `DRAINING`. Account mismatch, Puzzle navigation, calibration mismatch, opponent uncertainty, and user-disabled Auto Move therefore still admit different continuation decisions. Define one exhaustive mapping from each pause/failure reason to `canAutoMove`, next phase, and resume requirement.

- True two-threshold hysteresis remains an explicit unratified `[ASSUMPTION]` and still differs from the literal “inside the band or below uses +200” product statement. This is not a hidden implementation ambiguity anymore, but it remains a release-blocking product decision because the two policies produce different target-Elo sequences from the same results.

## Recheck 3 — Final focused pass

**Verdict:** CLEAN FOR CRITICAL/HIGH TECHNICAL BLOCKERS.

The corrected documents now normalize every durable phase and typed reason, assign drain timeout exactly to `ABORTED/UNRECONCILED_DRAIN_TIMEOUT`, persist and validate the consecutive-saturation control state, and define an exhaustive paused-state policy in which no paused phase can execute Auto Move before a committed reconciliation transition. No critical or high implementation blocker remains beyond the explicitly separated owner-ratification decision for true two-threshold hysteresis.
