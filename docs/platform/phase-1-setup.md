# Thinker platform — Phase 1

The Node monorepo coexists with the existing Python application. No Python runtime or local user database is migrated. No customer data, Bitcoin wallet material, credentials, worker deployment, or runtime license issuance is included in this bootstrap.

## Local verification

Use Node 22.12+ and pnpm 11.25.0. Run `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test`, then `pnpm db:local`. `pnpm dev:commerce` exposes a bootstrap liveness endpoint at `/health`; this endpoint does not claim database readiness or Access authentication. Every business path currently returns 404. Public Workers endpoints and preview URLs are disabled. The Worker has no runtime secrets.

The local command wrapper stores Wrangler state under the operating system's temporary directory, namespaced by a hash of this checkout. This avoids a reproduced Windows path-length failure in the repository's deep path: the default D1 state failed even on `SELECT 1`, while a short state path succeeded. Development and local migration commands share that state directory. Temporary data may be cleaned by the OS and contains fixtures only; it is not a production backup.

## Supabase

Apply `supabase/migrations/202610290001_license_foundation.sql` once through the authorized project's SQL editor. This creates `thinker_private`, `paid_grants`, `licenses`, `license_sessions`, `license_events`, and four isolated NOLOGIN/NOBYPASSRLS workload roles. All four tables enforce RLS with no permissive policies. Schema/table access is explicitly revoked from API roles and workload roles. No role memberships, login credentials, or broad service-role access are created. Keep `thinker_private` outside exposed API schemas.

This is a deny-by-default database foundation, not a functional license server. Phase 2 must add narrowly granted transactional functions and verified service identities. The issuer must check a valid, unexpired grant and insert its license in one PostgreSQL transaction. Revocation, HWID binding, session replacement, delivery envelopes, and grant invalidation are not implemented here. Do not enable issuance by directly granting table writes.

When a baseline was applied using SQL Editor, a later Supabase CLI migration rollout must first reconcile its migration history using the documented `supabase migration repair` workflow for version `202610290001`, after schema comparison. Do not reapply the baseline, silently skip failures, or alter unrelated project schemas.

## Data invariants and remaining service rules

UUID strings and UTC milliseconds are the D1 integration convention. D1 constraints enforce integer-positive prices, unique addresses and derivation indexes, one address per order, immutable issued invoice terms, immutable assigned addresses and output identity, output network correspondence, one current settlement per order, and output-to-settlement order correspondence. Service code in Phase 2 must additionally validate exact decimal quote syntax, ticket assignment at creation, address presence when issuing invoices, confirmed-output sums and policy, authorized payment transitions, monotonic versions, and license projection before fulfillment.

Supabase uses native UUIDs and timestamptz. Composite grant/license foreign keys prevent changing order, customer, plan, term, or activation deadline during issuance. Database constraints cannot prove blockchain payment or validate HMAC secrets. NOLOGIN roles have no capability until Phase 2 scoped functions and authenticated service routes exist. RLS does not constrain a project owner or bypassrls administrator.
